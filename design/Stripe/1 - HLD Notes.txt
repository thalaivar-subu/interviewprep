Core services: Checkout/tokenization (client side), Payment Service (intents + state), Ledger Service (double-entry), Webhook Receiver, Reconciliation Job.
Flow: card tokenized in the browser -> backend creates PaymentIntent with an idempotency key -> confirm -> issuer authorizes -> capture -> ledger entries written -> webhooks confirm each transition -> funds settle to the bank in ~2 business days -> daily reconciliation against Stripe's report.

READ THIS FIRST: the article answers a different question than "design Stripe"
The article describes building a payment system that *integrates with* Stripe -- you are the merchant, Stripe is the processor. An interviewer asking "design Stripe" usually means building the processor itself: the card-network integration, the PCI vault, the ledger at multi-tenant scale, webhook delivery infrastructure, payouts and multi-currency. Everything below is the merchant-side design, which is still the right answer to "design a payment system" and covers the genuinely hard parts (idempotency, ledger, reconciliation). Know which question you are being asked, and say so out loud.

The one rule that drives everything: money operations are not idempotent by nature, so you must make them so
A network timeout on a charge is ambiguous -- the request may have succeeded, failed, or still be in flight. The client cannot tell, so it retries, and a naive system double-charges. Every design decision below exists to remove that ambiguity.

Idempotency and double-charge prevention
  def charge(order_id, amount, idempotency_key):
      existing = idempotency_keys.get(idempotency_key)
      if existing: return existing.result           # replay, do NOT re-execute
      with db.transaction():                        # SERIALIZABLE
          order = orders.select_for_update(order_id)
          if order.status != PENDING: return order  # concurrent request already moved it
          order.status = CHARGING
      result = gateway.charge(amount, idempotency_key=idempotency_key)   # pass it downstream too
      idempotency_keys.put(idempotency_key, result)
      return result
Three layers of defence, and you want all three:
  1. Idempotency key -> cached result, so a retry replays instead of re-executing.
  2. DB unique constraint on (order_id, charge_status) -> a concurrent duplicate fails hard at the DB.
  3. Optimistic locking (version column) or SELECT FOR UPDATE -> serialises concurrent mutations of one order.
The key must be generated by the CLIENT (order_id or a UUID) and reused across retries of the same logical attempt. A server-generated key defeats the purpose, because a retry would generate a new one.
Generalizable: this is the same pattern as Uber's payment capture, Splitwise's settlement and Twitter's post -- any client-retriable write that has an external side effect.

Double-entry ledger
Every transaction writes two entries summing to zero:
  $100 charge:  debit customer_receivable +100,  credit revenue -100
  $100 refund:  debit revenue +100,              credit customer_receivable -100
Properties, all non-negotiable:
- **Append-only.** Never update or delete an entry. A mistake is corrected with a REVERSAL entry, so the error and its correction are both visible forever.
- **Balances are derived, never stored mutably**: balance(account) = SUM(amount) over its entries. A stored balance can silently drift out of sync with its entries; a derived one cannot.
- Index on (account_id, created_at) so balance queries are a single range scan.
- Single Postgres database with SERIALIZABLE isolation. **Do not shard the ledger.** Money correctness needs cross-account transactions to be atomic, and sharding turns those into distributed transactions -- the throughput you gain is not worth losing the invariant.
The zero-sum property is what makes the whole thing auditable: if SUM(all entries) != 0, you have a bug, and you can detect it without knowing anything about the business logic.

Payment state machine
  PENDING -> CHARGING -> CHARGED -> FULFILLED
Stripe's own PaymentIntent lifecycle runs alongside: requires_confirmation -> succeeded | payment_failed.
Two state machines, two systems, which is exactly why reconciliation exists.

Webhooks and delivery guarantees
Webhooks are at-least-once, unordered, and may arrive after you already know the outcome. Handle accordingly:
  1. **Verify the signature** first -- Stripe signs with a shared secret. An unverified webhook endpoint is an open door for forged "payment succeeded" events.
  2. **Deduplicate on event_id** in a processed_events table before doing anything.
  3. **Return 200 within 5 seconds**, then do the real work async. Slow handlers get retried, which amplifies load exactly when you are struggling.
  4. **Tolerate out-of-order delivery** -- check current state before transitioning, never blindly apply.
  5. **Never rely on webhooks alone.** Run a polling job every ~5 min querying recent PaymentIntents to catch anything missed. Stripe retries non-2xx with exponential backoff for up to 3 days, but a bug on your side inside a 200 response is invisible to it.
Point 5 is the real lesson: a push channel is an optimisation, never the source of truth. Always pair it with a pull-based sweep.

Reconciliation (daily)
  1. Download the settlement report.
  2. Match by payment_intent_id.
  3. Verify amounts and statuses agree.
  4. Flag: missing in ledger, missing in Stripe, amount mismatch.
  5. Investigate -- usual causes are webhook failures, race conditions, timezone boundary effects.
SLA: unresolved discrepancies older than 24h escalate to engineering leadership. Automate it and alert; a reconciliation job nobody looks at is worse than none, because it manufactures false confidence.

PCI compliance and tokenization
- Card data goes from the browser DIRECTLY to Stripe via Stripe.js/Elements; your server receives only a token. Raw PAN never touches your infrastructure.
- That choice is what puts you in **SAQ-A** (self-assessment, minimal) rather than **SAQ-D** (annual audit, network segmentation, encryption at rest, extensive documentation). The compliance burden difference is enormous and is the single strongest argument for tokenization.
- Never log card numbers or CVV. **Never store CVV at all** -- prohibited by the card networks outright, even encrypted.
- HTTPS everywhere on payment pages, regular vulnerability scanning.

Key timings
  settlement to bank        ~2 business days
  webhook retry window      up to 3 days
  webhook ack deadline      5 seconds
  polling reconciliation    every 5 minutes
  discrepancy escalation    24 hours

How Stripe ACTUALLY does it in production
Confidence: MIXED. Stripe publishes a lot about API design and engineering practice, much less about internal infrastructure. Marked per item.

- **Idempotency keys are Stripe's own contribution to the public canon** (HIGH confidence). Their engineering writing on designing idempotent, retry-safe APIs is the canonical reference for the pattern used above -- worth naming as prior art.
- **Date-based API versioning with response transformation** (HIGH confidence, and the most interesting thing here). Every Stripe account is pinned to the API version it was created on, and Stripe maintains backwards compatibility essentially indefinitely by running each response through a chain of version-gate transformations that downgrade the modern object shape back to whatever the caller expects. This is the opposite of the usual "v1/v2 endpoints, deprecate v1" approach and is a genuinely strong system-design talking point on API evolution.
- **Large Ruby codebase** (HIGH confidence). Stripe built and open-sourced **Sorbet**, a gradual type checker for Ruby, specifically because their monolith outgrew untyped Ruby. That a payments company invested in static typing is itself the argument: correctness over velocity.
- They open-sourced **Veneur** (observability/metrics aggregation) -- MODERATE confidence on current internal use.
- Datastore internals: reported to have run heavily on MongoDB early with in-house layers on top. LOWER confidence, and likely stale -- do not assert specifics.

Where reality diverges from the textbook answer
The generic design says "single Postgres, SERIALIZABLE, do not shard." That is right advice for a merchant's ledger, and wrong at Stripe's own scale -- a global processor cannot run every account's ledger on one primary. The real resolution is that ledgers shard by ACCOUNT (a tenant boundary), because cross-account atomicity is rarely needed, while cross-entry atomicity within one account always is. If pushed on "how does this scale", that is the answer: find the boundary the invariant does not cross, and shard there.

Gaps in the source article (NOT from this write-up)
- **Refunds, partial refunds and chargebacks/disputes.** Disputes especially: the money is clawed back weeks later, and the ledger needs entries for the reversal plus the dispute fee. This is where most real payment bugs live.
- **Payouts** to the merchant's bank, and the float between capture and settlement.
- Multi-currency and FX (see Splitwise for the rate-on-date-of-transaction pattern).
- **3D Secure / SCA**, which inserts an interactive challenge mid-flow and breaks the clean synchronous state machine above.
- Fraud scoring before authorization.

Related patterns list (see also Reference/Notes.txt)
- Idempotency key -> cached result: the canonical fix for retriable side-effecting writes (also Uber, Splitwise, Twitter).
- Append-only ledger with derived balances -- same "materialised view over an immutable log" idea as Splitwise's Balance table and event sourcing generally.
- Reversal entries instead of mutation -- same tombstone/append reasoning as Twitter's deletes.
- Push channel plus pull sweep: never trust webhooks alone as a source of truth.
- Verify-then-dedupe-then-ack for any inbound event handler.
- Shard at the boundary your invariant does not cross (per-account ledgers).
- Reduce compliance scope by never touching the sensitive data (tokenization -> SAQ-A).
